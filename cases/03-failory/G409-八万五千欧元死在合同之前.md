## 故事正文

Jan Johannes 是 Flux 的创始人兼 CTO，学过一点物理和哲学，主要是自学的全栈开发者。

Flux 的起点在大学。当时 Facebook 刚进德国，他们亲身经历过"所有消息和朋友都被锁在 studiVZ 数据筒仓里"的感觉。出发点一直是：让人拥有自己的数据，同时还能和不懂技术的普通朋友一起用主流社交产品。他们很快学到两件事：支持所有数据类型太多了，于是收窄到只做消息；替换现状不可能，于是转向做一个专业消息产品，把 Facebook、邮件这些已有渠道接进来。

产品没进入增长期，在私人 beta 就失败；等候名单上有几千人，来自演讲、路演和加速器曝光。

他的失败清单很长，其中任何一条都足够致命。

第一条是太早找投资，甚至根本不该找。这个产品对投资人本来就没那么有意思，他当时却以为只是自己不够努力。回头看，在柏林找大投资人这件事本身就很蠢——如果直接卖咨询、卖服务、卖定制，一边做一边把产品养出来，会走得远得多。他的判断来自美国博客和柏林创业圈里那些"希望世界是这样"而非实际经验的建议。

第二条是联合创始人匹配度差。他和商务联创性格相反，摩擦越来越多。他补了一句：联创最好认识超过一年再一起干，而他们是为了这个项目才认识的。他还高估了柏林的钱，以为商务合伙人能拿原型见 VC，顺手把办公室、招聘、财务、合同都办了；当时最缺的其实是有人一起做产品。

第三条是过度工程，他自己认账。他以为所有公司都会发布概念趋同的 REST API，于是做了一套连接和消费 REST 端点的 DSL，用 Erlang 写的；其实完全可以先手工写头几个连接器。这个决定的推手很隐蔽：投资人总在问"秘方是什么"，于是"连接器生成技术"变得极其重要——真正的动机是想先打动投资人。他还上了太早的微服务、边界也划错，允许开发者各用喜欢的语言，最后成了 Erlang、Go、Ruby、JavaScript 的混合体，人一进一出，支持成本激增。还有错位的技术理想主义：他想让整个架构为一个分布式、自包含的未来服务，那个未来没有来。

第四条是时机。起步时 Twitter 的 API 还很开放，Facebook 和 Google 都有 XMPP 消息接口；后来消息成了大事，它们转向封闭花园，旧接口没了，新接口还没开。唯一救他们的是从第一天就支持邮件。

最后杀死他们的是合同。终于转到企业客户时，跑道已经很低。一位投资人借了他们一位律师，但合同是没有尽头的兔子洞。等找到勉强可接受的版本，那家公司重组、对接人换了，他们已经没有跑道，而邮件里来了一版新合同，要求对项目绝大部分完全排他——他们永远不可能再把这个软件卖给第二个客户。

这就是结束。钱：融了约 7 万欧天使轮，另烧掉约 7 万欧私人储蓄供两人生活；放弃后为保住主体、收尾，他又花了 1.5 万欧。第一笔生意从未发生。

## 可用观点

- "秘方"是投资人给的诱饵：为了回答"你的护城河是什么"，团队会把工程资源投向可展示的复杂度，而不是可交付的功能
- 多语言栈的成本不体现在开发期，体现在人员流动时；每多一门语言，就多一份只有特定人才能维护的资产
- 企业合同的周期与创业公司的现金周期不同步，越接近成交越危险——它不是希望，是一笔要先垫付数月的赌注
